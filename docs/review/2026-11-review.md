# bioimaging code review, 2026-11

## Verdict

- The service layer works: 232 tests pass on the 15 real test files, and the backfill, live index and storage triage behave as designed in normal runs. No P0 was found.
- The riskiest paths are ordering ones. Old results are deleted before a new ticket is admitted, a superseded ticket that is still in flight is not cancelled on a retune, and errors are logged but not recorded in the registry.
- The repo's own test command and the `uv run` units can change production (data on /mmfs2, the production venv). Until the roadmap's first two items are done, use only the safe command in [CLAUDE.md](../../CLAUDE.md). Order of work: [docs/ROADMAP.md](../ROADMAP.md).

## Safety

Two things in this repo can change production, and one of them already did before this review began.

- **The test command.** `uv run pytest tests/` (README, old CLAUDE.md) or a bare `pytest` collects 11 scratch files that run at import. One (`tests/test_conver_to_zarr.py`) removes and rewrites two benchmark zarr dirs on /mmfs2; another writes `/tmp/mock_data`. Their modification times (benchmark dirs 2026-11-05 22:17:42 and 22:18:13, `/tmp/mock_data` 22:05) show they ran on 2026-11-05, before this review started (TI-01, TI-03). `test_watch_backfill` also opens the production registry through the live-index thread (TI-02).
- **`uv run` in three units.** `opym-backfill`, `opym-receive` and `opym-receive-backfill` run `uv run`, which re-syncs the production `.venv` on every start. Venv files were stamped 2026-11-05 22:17:02 and production restarted at 22:21 (OR-02, effect confirmed by the architect).

This review ran only the 15 real test files, with the registry, jobs dir, log dir and `HOME` redirected to a temp dir, and `uvx` for ruff and mypy. The T07 snapshots show the production registry, the benchmark zarrs, `/tmp/mock_data` and `/dev/shm/petakit_jobs` unchanged by that run (only the running service rewrote `stream_health.json` and `supervisor_status.json`). No `uv run` was used.

## Architecture notes

### Map

bioimaging is the services layer. `backfill/` (`cli.py` discovery, pool, watch loop, ticket collection, MIP and viewer dispatch; `pipeline.py` staging, tickets, admission, outputs; `viewer_export.py`; `mip_movie.py`; `live_index.py`; `log.py`) plus `backfill/storage_triage/` (9 modules, read-only, imports nothing from opym). Entry scripts: `run_backfill_cli.py`, `run_pipeline_cli.py`, `run_napari_opym.py`. `psf_tools/` (24 modules) is decon trial and PSF tooling; only `extraction_plan` is on the production path (imported at `backfill/pipeline.py:43`). `deploy/` holds the unit templates (6 of 7 match the live units; `opym-live-qc` differs, OR-01). Tracked strays: `scratch/`, `matlab_legacy/`, `data/` (7 small files), `.vscode/settings.json`, and 11 non-test scripts under `tests/`.

Console scripts: bioimaging owns `opym` (shadowed, OR-03), `naparym` (broken, PSF-01/02), `opym-backfill` and `opym-storage-triage`. The rest come from opym: `opym-serve`, `opym-receive`, `opym-receive-backfill`, `opym-backfill-send`, `opym-stream-watch`, `naparym-live`, `opym-live-trace`. `opym-add-times` is in the venv because opym is installed there.

Live units (all enabled and active 2026-11-06): `opym-serve` (`.venv/bin/opym-serve`), `opym-receive`, `opym-receive-backfill` and `opym-backfill` (all `uv run`), `opym-live-qc` (CORE venv), `opym-logrotate.timer` (hourly). ### Path matrix (decon x format)

`B` is the raw leaf dir itself, or the mirror root when it is unwritable.

| input format | decon | staged / crop input | final DSR dir | who reads it |
|---|---|---|---|---|
| OME-TIF | off | `B/processed_tiff_series_split/*.tif` (no staging) | `<dataDir>/DSR_nodecon` | `cli._dsr_dir_for` -> MIP encode, viewer export; opym-viewer does NOT find it |
| OME-TIF | on | same | `<dataDir>/Decon/DSR_decon`; intermediates `Decon/*.tif`, `Decon/psfgen` (reaped) | same, and opym-viewer |
| zarr (flat or nested) | off | `B(leaf)/decon_stage/<prefix>_C<c>_T<ttt>.tif` (rot90 `(ny,nx,nz)`) | `decon_stage/DSR_nodecon` | `_dsr_dir_for`; staged TIFFs reaped |
| zarr (either layout) | on | same | `decon_stage/Decon/DSR_decon` | `_dsr_dir_for`; the live lane writes the same path; opym-viewer |
| zarr, one-format live lane | on | in memory | `B(leaf)/viewer/<leaf>_dsr.ome.zarr` | `processed_store_for`; `_run_mip_encode` |

A re-run in a different decon mode keeps the other mode's dir by design. `_dsr_dir_for` uses the CURRENT env PSF, not the PSF the row recorded, so a registry `output_path` can point at a dir the current config never writes. The old `zarr_mirror/DSR_nodecon` outputs (mirrored handedness, opym PROC-F1) are looked up nowhere.

### Storage triage: delete-safety verdict

The tool does not and cannot delete data. Over `backfill/storage_triage/*.py` and the notebook scripts, every filesystem-mutating call is on its own sqlite file (`<work-dir>/storage_triage.sqlite3`, `storage_verdicts.sqlite3` via temp plus replace), the dated report directory (`suggestions.csv`, `paths_tier*.txt`, `review_queue.csv`, `notes.txt`, `summary.json`), or a scratch dir given on argv. No path under `/dev/shm`; no `unlink`, `rmtree` or `rename` on data; the registry and other DBs are opened `mode=ro`. The risk is in the suggestions, not the tool: `verify` does not re-check the keeper (ST-01), zarr channels beyond channel 0 are not proven identical (ST-02), aliases are not detected (ST-03), the cache can be stale (ST-05), and A3 is not always safe to follow (ST-04). The PI deletes; nothing here consumes the lists automatically.
